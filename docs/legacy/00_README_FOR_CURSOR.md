## Краткий технический контекст

«Личный космос» — сервис разовых персональных натальных разборов. Сервер сам рассчитывает карту, передаёт выбранные показатели внешнему ИИ, сохраняет текст и PNG, локально собирает PDF. Одно право на услугу возникает из кода доступа либо подтверждённой банковской покупки.

Стек: Go 1.26, стандартный `net/http`, PostgreSQL 16, Vue 3 + TypeScript + Vite. Компоненты веб-контура на VPS: API, PostgreSQL и Caddy. Генерация выполняется внутри API; очередь хранится в заказах; допускается один активный worker на базу. Внешнего брокера очередей нет.

Основные сущности:

1. `Account` — подтверждённый почтовый аккаунт.
2. `Checkout` — банковская покупка одного или нескольких разборов.
3. `AccountAccess` — одно право на услугу с отдельным черновиком.
4. `Order` — зафиксированная анкета, карта и материалы одного разбора.
5. `WebTicket` — вопрос пользователя и сохранённый ответ владельца.

Без почтового аккаунта действующий код также может открыть самостоятельную кодовую сессию и один заказ. Это отдельный путь; перенос в кабинет выполняется явной привязкой кода.

## Инварианты для разработки

1. Один доступ создаёт один заказ с одной зафиксированной анкетой. Повтор возвращает прежний заказ; другая анкета после использования конфликтует.
2. Карту рассчитывает программа. При неизвестном времени нельзя придумывать дома, углы и точный момент рождения.
3. Действующий контракт текста — **1800–2700 слов**, не символов, включая неизвестное время рождения.
4. Открытие результата, скачивание и сборка PDF не вызывают ИИ. Принятые этапы используются повторно.
5. Неизвестный исход платного запроса требует проверки. Нельзя обходить остановку удалением checkpoint или повторной оплатой того же этапа без разбора исхода.
6. Сервер определяет сумму, принадлежность, оплату и право на генерацию. Возврат браузера от банка не является подтверждением платежа.
7. Источник доступа проверяется перед платными этапами. Блокировка/возврат прекращают право на новые вызовы; сохранённые материалы не удаляются автоматически.
8. Почтовая и кодовая идентичности объединяются только предусмотренной привязкой кода. Административная роль не следует из клиентского входа.
9. Совместимость пары, личный год, Seller API Ozon и эквайринг Ozon Банка не реализованы.
10. Секреты и реальные клиентские данные не нужны в контексте агента: используйте имена переменных и синтетические примеры.
