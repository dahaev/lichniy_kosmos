# Личный космос: функциональное описание продукта

Дата: 10.11.2026. Описываемая версия исходников: **0.13.4**. Редакция 2: только веб-продукт. Метод и границы проверки — в `00_README_FOR_CURSOR.md`. Полный каталог путей и их ветвей — в `04_USER_JOURNEYS.md`.

## 1. Что это за проект

«Личный космос» — русскоязычный цифровой сервис, который по данным рождения создаёт сохраняемый персональный материал: рассчитанную натальную карту, символическую интерпретацию, художественную иллюстрацию и PDF.

Продукт предназначен для знакомства с астрологическими символами и саморефлексии. Его собственные тексты объясняют, что астрология не является научно подтверждённым методом оценки личности или предсказания событий. Формат не предполагает медицинских диагнозов, гарантированных событий или финансовых/юридических рекомендаций.

Канал использования в этом описании — самостоятельный сайт `lichny-kosmos.ru`. Код, полученный у продавца или на внешней площадке, активируется на сайте. Автоматического Seller API Ozon для выдачи кодов в рассматриваемом коде нет.

### Состав одного результата

| Часть | Назначение | Кто создаёт |
|---|---|---|
| Натальная карта | Положения тел, знаки, движение, аспекты; при подходящих данных также дома и углы | Локальный серверный расчёт |
| Текст | Восемь тематических разделов и вопросы для размышления | Внешний ИИ по рассчитанным показателям с серверной проверкой |
| Иллюстрация | Метафорический художественный образ по мотивам карты | Внешний генератор изображений |
| PDF | Объединённый документ с анкетой, картой, текстом, иллюстрацией и пояснениями | Сервер локально из сохранённых материалов |

Иллюстрация — художественная часть, а не точная схема натальной карты. Эти виды результата не взаимозаменяемы.

## 3. Пользователи и роли

### Посетитель сайта

Может открыть главную, каталог, страницы услуг, описание работы, пример формата разбора, FAQ, журнал и публичный контакт поддержки. Просмотр общедоступных материалов не требует аккаунта. Посетитель выбирает, разрешать ли необязательную статистику посещений.

### Пользователь с кодом

Входит по действующему коду, заполняет анкету, подтверждает её, создаёт один разбор и возвращается к его материалам. Вход и проверка кода сами по себе не расходуют право на результат. Передача кода третьему лицу фактически передаёт возможность входа до привязки к аккаунту; парольного кабинета у кодовой идентичности нет.

### Пользователь почтового кабинета

Подтверждает почту одноразовым кодом. Может закреплять коды за аккаунтом, видеть несколько доступных услуг и результатов, хранить отдельную анкету для каждого доступа и просматривать собственные банковские покупки. Один подтверждённый адрес соответствует одному аккаунту.

### Владелец

Входит по отдельному ключу на `/owner`. Сервер проверяет административное право. Доступны реестр кодов, настройки банковских продаж, покупки, веб-обращения и статистика. Клиентский код и вход по почте административных прав не дают.

Отдельных административных почтовых аккаунтов, панели ролей и самостоятельной роли оператора веб-поддержки в этой версии нет. Для совместной работы владельцев потребуется согласованная модель доступа; наличие двух участников команды само по себе не создаёт два независимых административных входа.

## 5. Сценарий: вход в кабинет по почте

1. Пользователь вводит email.
2. Сервер проверяет формат адреса и ограничения частоты, создаёт шестизначный код и отправляет письмо через настроенный SMTP.
3. Пользователь вводит код. Он действует 10 минут, допускает до пяти неверных попыток и используется один раз.
4. Сервер создаёт аккаунт либо возвращает существующий аккаунт того же адреса и открывает сессию на 24 часа.
5. Кабинет показывает доступы, разборы и покупки этого аккаунта.

Если SMTP не подключён или письмо не удалось отправить, пользователь получает сообщение о недоступности входа. Сервис не выдаёт сессию на основании одного введённого адреса. Пароль, его восстановление и изменение email через пользовательский API не реализованы.

Основания: `internal/app/account_http.go:37`, `internal/app/account_postgres.go:35`, `internal/app/auth.go:73`.

## 6. Сценарий: использование кода

### Без почтового аккаунта

1. Код выпущен владельцем и его партия разрешена для сайта.
2. Пользователь вводит код; сервер открывает кодовую сессию.
3. Если код ещё не использован, доступна анкета. Если разбор уже создан этой кодовой идентичностью, возвращается существующий заказ.
4. Код связывается с конкретной анкетой и заказом только при успешном сохранении расчёта.
5. Повтор с той же анкетой возвращает сохранённый заказ; другая анкета после использования отклоняется.

### В почтовом кабинете

1. Пользователь вводит код после входа по почте.
2. Сервер закрепляет право на услугу за одним аккаунтом.
3. Для этого доступа появляется собственная анкета. В одном кабинете можно иметь несколько таких доступов.
4. Уже готовый кодовый результат можно привязать к почтовому аккаунту с сохранением ID заказа и материалов. Во время активной генерации перенос откладывается.
5. После переноса прежний вход по этому коду больше не открывает перенесённый результат как независимому кодовому пользователю.

Повторная привязка тем же аккаунтом безопасна; попытка забрать код другим аккаунтом отклоняется. Привязка права на услугу и его окончательное использование для создания заказа — разные действия.

Основания: `internal/app/web_postgres.go:11`, `internal/app/account_postgres.go:145`.

## 7. Анкета и подтверждение

Пользователь указывает:

- Имя: от 1 до 60 символов.
- Дату рождения: от 1900 года до текущего дня по Москве.
- Место рождения: выбор из серверного справочника.
- Время рождения либо признак «неизвестно».
- Источник времени: документ, сведения семьи или приблизительная оценка.
- Возможную погрешность: не указана либо ±15, ±30, ±60 минут.

Справочник содержит 565 273 населённых пункта и варианты названий. Можно искать современные, местные и некоторые исторические названия, различать одноимённые места по региону/стране и проверить выбранную точку на внешней карте по явному действию. Произвольный адрес, координаты и часовой пояс из браузера не принимаются как источник расчёта.

Черновик сохраняется на сервере после валидации. Для почтового аккаунта черновик относится к конкретному доступу; в прежнем сценарии — к пользовательской идентичности. Перед заказом пользователь проверяет анкету и подтверждает актуальную версию согласия на создание материалов.

Если местное время пришлось на пропуск или повтор при переводе часов, сервер просит уточнить данные. Он не выбирает подходящий UTC-момент молча.

Основания: `internal/app/model.go:63`, `internal/places/catalog.go`, `internal/app/account_http.go:146`.

## 8. Расчёт карты

Расчёт выполняется локально и не требует обращения к ИИ или платному геокодеру.

Он включает Солнце, Луну и восемь планет от Меркурия до Плутона: положения, знаки, долготы, скорость и направление движения, основные аспекты. При известном времени рассчитываются ASC, MC, DSC, IC и дома Плацидуса, когда эта система определена для выбранных условий.

При приблизительном времени учитывается диапазон: возможные знаки и дома, устойчивые аспекты и предупреждения. При неизвестном времени рассматривается весь местный день, а точное время рождения, дома и углы не выдумываются. На полярных широтах неопределимые дома Плацидуса не заменяются другой системой автоматически.

В заказе сохраняются версия расчёта, исходная анкета, выбранное место и результат. Повторное открытие не пересчитывает историческую карту новой версией движка.

Основания: `internal/astro/chart.go:15`, `internal/astro/chart.go:150`, `internal/app/calculation.go:13`.

## 9. Создание текста и иллюстрации

После сохранения карты заказ может быть поставлен в фоновую очередь. Пользователь видит текущий этап; закрытие вкладки не отменяет серверную работу. Обновление страницы восстанавливает состояние заказа.

1. Сервер выбирает допустимые рассчитанные показатели и сведения об их неопределённости.
2. Внешний ИИ создаёт структурированный русский текст и описание художественного образа.
3. Сервер проверяет структуру, ссылки на рассчитанные показатели, объём и ряд недопустимых элементов.
4. При полном корректном, но коротком ответе предусмотрена ограниченная доработка. В режиме AITUNNEL общий короткий текст дополняется новыми абзацами.
5. Принятый текст сохраняется. Только после этого запрашивается изображение.
6. Сервер проверяет PNG 1024×1536 и сохраняет его. Заказ становится готовым.

Разбор содержит восемь тем: общая картина, характер, эмоции, мышление и общение, отношения, работа и самовыражение, противоречия/рост, применение в повседневной жизни. Затем идут вопросы для размышления. Контракт публикации — **1800–2700 слов**, включая резюме, названия разделов и вопросы; описание изображения и подписи символов не входят в этот счётчик.

Исходные имя, почта, дата/время/город рождения и коды не включаются в текстовый промпт. Это минимизация передаваемых данных, а не самостоятельное доказательство полной анонимности или юридического соответствия.

В текущем коде предусмотрены прямой OpenAI и два фиксированных варианта подключения AITUNNEL. Выбор режима и моделей — настройка сервера; пользователь не задаёт собственный ключ или поставщика в интерфейсе.

Основания: `internal/app/generation.go`, `internal/app/generation_prompt.go`, `internal/app/openai.go`, `internal/app/reading_expansion.go`.

## 10. Ошибки и продолжение

- Ошибка расчёта до фиксации заказа не расходует доступ.
- Ошибка картинки не требует заново создавать принятый текст.
- Готовые этапы сохраняются; новый код или новая оплата для продолжения того же заказа не нужны.
- Некоторые явные отказы поставщика допускают продолжение после устранения причины.
- Таймаут, неполный ответ, обрыв или неопределённый исход переводят заказ на проверку. Пользователь сайта или покупатель не может самостоятельно разрешить потенциально повторный платный вызов.
- После перезапуска сервер восстанавливает готовые этапы из файлов. Неизвестный платный запрос не отправляется заново автоматически.
- Исторический демонстрационный заказ без рассчитанной карты нельзя превратить в полноценный результат незаметным пересчётом.

## 12. Покупка на сайте

Механизм реализован, но открытие продаж требует отдельного подключения и заполненных настроек.

1. Пользователь выбирает от одного до пяти натальных разборов.
2. Сервер рассчитывает стоимость по своей цене и возвращает версию предложения.
3. Покупатель входит в почтовый кабинет и принимает актуальные условия.
4. Создаётся банковский заказ с зафиксированной суммой и позициями.
5. Пользователь переходит на размещённую форму банка. Карточные данные через сервер проекта не проходят.
6. Сервер проверяет платёж через адаптер банка. Возврат браузера на сайт сам по себе оплату не подтверждает.
7. Подтверждённый заказ выдаёт по одному доступу на каждый оплаченный разбор.
8. Каждый доступ используется отдельно: собственная анкета, заказ и результат.

Реализован адаптер **Т-Банка**. Эквайринг Ozon Банка и автоматическое оформление возврата через банковский API не реализованы. Полученные от банка события полного или частичного возврата обрабатываются: дальнейшее использование соответствующих доступов блокируется, частичный возврат требует проверки.

## 13. Поддержка на сайте

В коде реализована веб-форма обращения. Её показ зависит от сборки: если в настройках страницы выбран внешний контакт, вместо формы отображается этот контакт. Для описанного здесь пути поддержки должна быть включена именно веб-форма; фактическая сборка не проверялась.

Неавторизованный посетитель видит справочные подсказки и переход к разделу о сервисе. После входа по почте или коду пользователь может написать вопрос 5–3000 символов, посмотреть свои обращения и обновить список ответов. Из результата можно открыть форму с привязанным номером своего заказа.

Владелец открывает `/owner/support`, читает обращения и сохраняет ответ до 5000 символов. Пользователь читает его на сайте при следующем открытии или обновлении списка. Автоматического письма об ответе нет.

Это модель «вопрос + одно поле ответа»: изменение ответа владельцем заменяет прежнее поле. Истории диалога, вложений и отдельной операторской роли нет. До входа отправить вопрос нельзя; если пользователь потерял код и не может подтвердить почту, самостоятельного пути восстановления через эту форму нет — нужен отдельный продуктовый сценарий.

Основания: `frontend/src/WebSupport.vue`, `internal/app/web_support.go:28`, `internal/app/web_support_store.go`.

## 15. Что учитывать при развитии продукта

1. Продажа, доступ к услуге и создание конкретного результата — отдельные процессы.
2. Генерация зависит от внешнего поставщика, баланса и контроля качества; обещание мгновенной готовности кодом не обеспечено.
3. Сохранённый результат и история клиента должны переживать обновления приложения.
4. Согласие на статистику отделено от входа, покупки и генерации. Отказ не блокирует основной продукт.
5. Будущие услуги потребуют новых серверных сценариев, контрактов данных, оплаты и тестов; одной карточки в каталоге недостаточно.
6. Статус регистрации товарного знака и допуск площадки — внешние процессы. Их завершение не включает интеграции в коде автоматически.
