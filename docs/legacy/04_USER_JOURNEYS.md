# Личный космос: все пользовательские пути веб-продукта

Дата: **10.11.2026**. Исходники: **0.13.4**. Редакция документации: **2**.

## 1. Границы и правила чтения

Документ охватывает найденные в коде пути самостоятельного сайта: публичное знакомство, почтовый и кодовый вход, кабинет, покупку, анкету, создание результата, скачивание, возвращение, поддержку и действия владельца. Для каждого основного этапа перечислены успешные, альтернативные, прерванные и ошибочные ветви. Произвольные комбинации действий пользователя сводятся к этим переходам и состояниям; документ не является утверждением о проверке всех сочетаний браузеров, сети и production-настроек.

Обозначения:

| Метка | Значение |
|---|---|
| **Код** | Ветвь существует в исходниках 0.13.4 |
| **Настройка** | Код есть, но путь требует включённой функции или подходящей сборки |
| **Пробел** | Самостоятельный путь не реализован; ниже указано, где он заканчивается |
| `U…` | Клиентский сценарий |
| `O…` | Сценарий владельца |
| `X…` | Общее условие, применимое к нескольким путям |
| `G…` | Отсутствующая возможность, которую нельзя обещать пользователю |

Это документация существующего веб-контура, а не новая реализация. Состояние рабочего сайта не проверялось. Подробности серверных контрактов — в `02_SERVER_FUNCTIONALITY.md` и `03_API_REFERENCE.md`.

## 2. Основные сквозные маршруты

### A. Новый клиент с кодом, через почтовый кабинет

1. Получает код у продавца или на внешней площадке. Автоматическая доставка кодов площадкой находится за пределами текущей серверной реализации.
2. Открывает сайт, при необходимости читает карточку услуги, пример и пояснения.
3. Открывает «Личный кабинет», вводит почту, получает письмо и подтверждает шестизначный код.
4. В кабинете вводит код доступа. Сервер закрепляет услугу за этим аккаунтом.
5. Нажимает «Заполнить анкету», вводит данные рождения и выбирает место из справочника.
6. Нажимает «Проверить данные»: черновик сохраняется на сервере, открывается подтверждение.
7. Проверяет данные и согласие, нажимает «Создать мой разбор».
8. Сервер рассчитывает карту, фиксирует заказ и использованный доступ; при разрешённом ИИ ставит генерацию в очередь.
9. Пользователь видит этапы, затем карту, текст и иллюстрацию; скачивает PDF/TXT/PNG.
10. Позже входит по той же почте и открывает сохранённый результат без новой оплаты и генерации.

Связанные ветви: U13–U22, U31–U44, U65–U105.

### B. Новый клиент с кодом, без почтового кабинета

Открывает `/activate` → вводит код → получает кодовую сессию → заполняет анкету → проверяет и подтверждает данные → создаёт заказ → ожидает материалы → читает/скачивает. Для возвращения использует этот же код. Подтверждать почту перед таким заказом не обязательно.

Код до привязки фактически является ключом доступа. Позднее клиент может войти по почте и явно привязать этот код, перенеся результат в кабинет. Вход по почте сам по себе перенос не выполняет.

### C. Новый клиент покупает на сайте

Каталог или карточка натальной карты → корзина с 1–5 разборами → серверная стоимость → почтовый вход → принятие условий → создание `Checkout` → открытие страницы банка → оплата → серверное подтверждение → появление доступов в кабинете → отдельная анкета и заказ для каждого доступа → материалы.

Путь требует `sales_ready=true`, подключённого банка и остальных настроек продаж. Данные рождения вводятся **после** подтверждения оплаты, отдельно для каждого разбора. Покупка нескольких разборов не является расчётом совместимости.

### D. Возвращение к существующему результату

По почте: вход → кабинет → нужная услуга → результат. По непривязанному коду: `/activate` → тот же код → существующий результат. По сохранённой ссылке: восстановление сессии → проверка принадлежности → результат; при отсутствии подходящего входа потребуется авторизация.

На странице открывается фактическое состояние: карта, активная генерация, остановка, частично готовые материалы либо полный результат. Повторное открытие не запускает новый ИИ-запрос.

### E. Перенос кодового результата в кабинет

Вход по почте → ввод прежнего кода → проверка отсутствия активной генерации и чужой привязки → перенос заказа с тем же ID и файлами → результат в кабинете. Связанные веб-обращения тоже переносятся. После этого для доступа используется почта; самостоятельный вход по коду к перенесённому результату прекращается.

### F. Продолжение незавершённого заказа

Открыть сохранённый заказ → прочитать состояние → при известной исправимой ошибке и разрешённом продолжении дать согласие → «Продолжить создание» → получить только недостающий этап. Если исход платного запроса неизвестен, клиентская кнопка повтор не разрешает: путь ведёт в поддержку и проверку владельцем.

### G. Вопрос через сайт

Войти → открыть «Поддержка» из меню или результата → написать вопрос → сохранить обращение → позже открыть список и нажать «Обновить» → прочитать ответ владельца. Из результата передаётся его номер. Этот путь требует отображения веб-формы в сборке; настройку надо проверить.

### H. Несколько услуг в одном кабинете

Клиент добавляет несколько кодов и/или оплачивает несколько разборов → видит отдельные доступы → выбирает один → заполняет его анкету → создаёт один заказ → возвращается в кабинет → повторяет для другого доступа. Черновики и результаты не должны смешиваться. Выбор готовой услуги открывает её результат вместо новой анкеты.

| U121 | Обращения временно не загружаются или превышен лимит 5 новых вопросов в минуту | Обновить позже / подождать; не отправлять много копий. При известном сохранении вопрос остаётся на сервере | Код |
| U122 | Не может войти ни по почте, ни по коду, но нужна помощь | Веб-форма не даёт анонимной отправки. Независимый канал восстановления с проверкой владения нужно спроектировать | Пробел |

Для вопроса по checkout интерфейс передаёт в поддержку общий переход, а поле `order_id` относится к разбору, не банковской покупке. Номер банковской покупки придётся указать текстом; отдельная структурированная привязка обращения к checkout отсутствует.

## 17. Владелец: все основные административные пути

| ID | Вход и действия | Результат / альтернативы | Статус |
|---|---|---|---|
| O01 | `/owner` → отдельный ключ → вход | Сервер проверяет ключ и роль; неверный ключ не открывает администрирование. Обычный клиентский вход не подходит | Настройка |
| O02 | Открывает защищённый `/owner/*` без роли | Видит вход владельца; успешный вход не для каждой страницы сохраняет прежнюю цель — это не универсальный механизм возврата | Код |
| O03 | Создаёт партию 1–500 кодов действующего продукта | Prepared-коды и партия сохраняются; повтор с тем же ключом не должен дублировать партию | Код |
| O04 | Просматривает партии, ищет код, применяет фильтр состояния/источника | Видит маски и счётчики; расшифровка конкретного кода требует рабочего ключа хранилища и аудируется | Код |
| O05 | Выпускает prepared-партию для сайта | Коды переходят в issued и становятся пригодны для клиентского входа/привязки; создание партии само этого не делает | Код |
| O06 | Выгружает CSV партии | Получает краткоживущую ссылку на экспорт подходящих кодов. При истечении создаёт новую выгрузку; неправильный ключ/отозванный экспорт не обходятся | Код |
| O07 | Блокирует неиспользованный код или партию с причиной | Prepared/issued закрываются для использования, выгрузки партии отзываются по правилам. Уже activated-код обычным действием блокировки не обрабатывается | Код |
| O08 | Просматривает журнал кодов и встроенный roadmap | Видит события/план; это не редактор продукта и не автоматическое выполнение пунктов roadmap | Код |
| O09 | `/owner/shop` → цена, продавец, условия и фискальные настройки → сохранение | Сервер проверяет revision и готовность; незаполненные prerequisites не позволяют открыть реальные продажи | Настройка |
| O10 | Смотрит банковские покупки и сверяет конкретный платёж | Сервер обращается к банку; неизвестный итог требует проверки, а не ручного клиентского флага paid | Настройка |
| O11 | `/owner/support` → вопрос → ответ → сохранить | Ответ становится доступен клиенту на сайте; повторное сохранение меняет одно поле, не добавляет реплику в чат | Код |
| O12 | `/owner/statistics` → период 1/7/30/90 дней | Видит посещения с согласием, регистрации, текущие состояния разборов периода и разрезы; это не отчёт о выручке и не точная конверсия всех посетителей | Код |
| O13 | Нужно исправить анкету, повторить неизвестный платный запрос, удалить аккаунт или открыть любой чужой результат | Универсальной административной кнопки для этих операций нет. Нужна отдельная проверяемая техническая процедура/доработка | Пробел |
| O14 | Два участника команды хотят независимые права и аудит своих действий | Сейчас настроен отдельный web-вход владельца, но нет кабинетов администраторов с почтой и панели ролей. Разделение доступа — новая задача | Пробел |

Техническое восстановление после ошибки ИИ, обновление, бэкап и миграция выполняются серверными инструментами; пользовательские пути не должны показывать команды сервера и секреты. Расписание копий и актуальное развёртывание требуют отдельной проверки окружения.

## 18. Сквозные условия и восстановление

| ID | Ситуация | Правило поведения |
|---|---|---|
| X01 | Истекла сессия во время защищённого запроса | Сервер отклоняет запрос; нужен повторный вход. Интерфейс не на каждом 401 автоматически перенаправляет на login — может сначала показать ошибку |
| X02 | Обрыв ответа после отправки создающей операции | Отличать неизвестный исход от подтверждённого отказа. Проверить сохранённые объекты и повторять ту же операцию с прежним ключом, где он предусмотрен |
| X03 | Одновременное использование одного права | Серверные транзакции/уникальности должны оставить один заказ/доступ. Разные анкеты не сливаются и не заменяют друг друга |
| X04 | Пользователь подменил ID, сумму, принадлежность или признак оплаты | Сервер проверяет право и собственные данные; чужой объект не становится доступным через клиентскую навигацию |
| X05 | Поставщик ИИ или банк недоступен | Ранее сохранённые данные сохраняются. Доступность чтения конкретного файла зависит от действующего входа и состояния хранилища; новый внешний запрос не заменяет проверку |
| X06 | БД/диск недоступны, файл повреждён | Показывать ошибку и проверять согласованность. Нельзя объявлять материал утраченным или автоматически повторять платный этап только по одной ошибке чтения |
| X07 | Пользователь отказался от статистики | Не блокировать вход, покупку, использование кода, генерацию, файлы и поддержку |
| X08 | Изменились условия/конфигурация между экранами | Проверять актуальную серверную версию перед действием; старый открытый экран не является разрешением обойти новые ограничения |
| X09 | Очистка браузера или выход | Отличать локальные корзину/выбор/несохранённый ввод от серверных аккаунтов, черновиков, заказов и файлов |
| X10 | Демонстрационный режим | Только явное тестовое окружение: синтетический вход/доступ, имитация покупки без денег, тестовые материалы. Его нельзя описывать как бесплатную production-продажу |

## 20. Как использовать каталог в разработке

1. Выберите конкретные `U/O/X/G` и сформулируйте ожидаемые переходы до/после изменения.
2. Для существующего пути найдите серверный контракт из `03_API_REFERENCE.md`; для пробела сначала согласуйте продуктовые правила.
3. Проверяйте хотя бы успешную ветвь, отказ, повтор, чужой объект и возвращение после прерывания, если они затронуты задачей.
4. Не создавайте отдельный тест на каждую строку этого документа механически. Выбирайте проверки риска и переходов, которые реально меняет задача.
5. После реализации обновляйте статус, критерии и источники этого пути, чтобы будущий агент не принял план за готовую функцию.

Основные источники: `frontend/src/App.vue` (`syncRoute`, `checkCode`, `useAccess`, `review`, `create`, `openOrder`, `accountLogin`), `AccountLogin.vue`, `AccountDashboard.vue`, `CartView.vue`, `CheckoutView.vue`, `CityPicker.vue`, `GenerationPanel.vue`, `ReportView.vue`, `WebSupport.vue`, `StatisticsConsent.vue`; серверные `internal/app/account*`, `web*`, `shop*`, `generation.go`, `download.go`, `pdf.go`, `internal/accesscodes/*`, `internal/sitepay/*`.
