# Личный космос 2.0 — SCREEN_SPEC MVP v2

Дата: 2026-11-11. Статус: проект спецификации после выбора пути A; подлежит визуальному утверждению. Это не инструкция писать код немедленно.

## 0. Основание
- `PRODUCT_MVP_SCOPE_v1.md`: границы MVP.
- Пять документов `00–04` версии 0.13.4: источник старого бизнес-поведения, но не новая архитектура.
- Утверждённый скриншот главного экрана 11.11.2026: визуальный эталон. Статичные изображения не фиксируют тайминги, easing и реализацию WebGL.
- Новое продуктово-UX решение владельца: **CTA «Построить мою карту» ведёт в анкету до ввода кода/входа**.
- Пишем новый код: Go + Vue 3 + TypeScript + PostgreSQL. Не переносим исходную реализацию.

## 1. Общая стратегия пути A

**Анонимный посетитель:** `/` → `/create` (четыре шага) → `/create/review` → `/create/access` (код или email) → подтверждение условий → сервер создаёт заказ ровно один раз → `/orders/:id/creating` → `/orders/:id`.

**Аккаунт с доступом:** после анкеты `/create/access` может показать выбор свободного доступа (один или несколько), затем подтверждение и создание; не требовать новый код.

**Кодовый посетитель:** после анкеты вводит действующий ещё не использованный код, получает право продолжить без email; после создания возвращается по коду. Рекомендуем предложить добровольную привязку к email ПОСЛЕ получения результата, но не блокировать создание.

**Существующий результат:** использованный код не становится новым доступом; показать предложение открыть прежний результат, сохранив нынешнюю гостевую анкету для другого кода. Нельзя тихо переписывать уже созданный профиль.

**Нет кода:** экран сообщает способы получения доступа и позволяет вернуться/сохранить черновик. В MVP нет собственной оплаты и нет автоматической выдачи Ozon API.

## 3. SCR-01 Главная
- **Визуальный источник:** утверждённый скриншот: огромная планета справа с золотой подсветкой, орбиты, ночной пейзаж, тёмно-синяя палитра, слева «У каждого — свой космос.», кнопки «Построить мою карту» и «Смотреть пример».
- Основной CTA ведёт прямо на `/create`, не к оплате и не к активации.
- Контекст входа не меняет смысл CTA; существующий пользователь при необходимости может выбрать готовый доступ после анкеты.
- При переходе визуальная сцена трансформируется (точная траектория задаётся в `MOTION_SPEC.md`).
- Добавить доступные пути к кабинету и прямой активации, не разрушая утверждённую композицию.

## 4. SCR-02 Анкета: четыре шага

### Шаг 1 «Как тебя зовут?»
- Поле `name`, trim, 1–60 Unicode-символов; фронт и сервер проверяют ввод.
- `Далее` только при корректном значении. Enter вызывает обычную проверку, не создаёт заказ.

### Шаг 2 «Когда ты родился?»
- `birth_date` формата YYYY-MM-DD; 1900 — текущая московская дата; календарный ввод.
- Кнопки «Назад» и «Далее», явные сообщения об ошибках.

### Шаг 3 «Где началась твоя история?»
- Поиск по справочнику; выбор строки с городом, регионом и страной; хранить **city_id**, а не произвольный текст.
- При редактировании текстового запроса ранее выбранный city_id сбрасывается.
- Ищем с debounce, показываем loading/empty/error; координаты и часовой пояс определяет сервер, а не браузер.
- Для MVP доступ гостя к поиску требует нового публичного ограниченного endpoint или гостевой сессии; старый `GET /api/cities` требовал Session. Это новая архитектурная задача.

### Шаг 4 «В какое время ты родился?»
- Выбор «Время известно» / «Время неизвестно».
- При известном: `HH:MM`, источник `document|family|approximate`, погрешность `0|15|30|60` минут.
- При неизвестном: очищаем точное время, присваиваем `time_source=unknown`, `accuracy_minutes=0`.
- Объяснить ограничения точности. Не показывать обещаний о домах/ASC для неизвестного времени.

### Общие правила анкеты
- Визуализация: единая космическая сцена, крупный заголовок вопроса, одно тематическое поле/группа и счётчик 01/04; не превращать в generic dashboard.
- Смена шагов сопровождается плавным motion, но поля должны быть доступны с клавиатуры.
- При возврате значения не исчезают.
- Гостевой черновик в MVP **предлагается сохранять только в `sessionStorage`** в пределах вкладки до появления аккаунта/кода; это решение ещё требует утверждения из соображений приватности. Не считать это серверным хранением. Предупредить, что удаление данных вкладки может стереть черновик; если нужна долговременная сохранность без входа — спроектировать отдельный ограниченный server draft и правила срока жизни.
- Не отправлять информацию о рождении в аналитику и не передавать её в URL.

## 5. SCR-03 Review
- Полный профиль: имя, дата рождения, выбранное место, время/неизвестно, источник и точность.
- Каждый блок имеет «Изменить» с возвратом на нужный шаг, сохранением остальных полей.
- Проверить клиентскую валидность, а серверная повторная валидация обязательна перед созданием заказа.
- CTA «Продолжить» → `/create/access`. Здесь **нет** фиксации заказа и расхода кода.

## 6. SCR-04 Доступ после анкеты
- Заголовок не должен обещать, что карта уже рассчитана; использовать «Данные заполнены. Остался доступ к персональному разбору».
- Вариант A: поле кода, проверить; неверный/заблокирован/лимит/чужая привязка показываются без утечки деталей.
- Вариант B: «Войти по email» → OTP, затем возврат к гостевой анкете; если есть свободные доступы, выбрать нужный.
- Если действующий код уже использован: показать «По этому коду уже создан разбор», кнопку открыть его при допустимой сессии и возможность использовать другой код. Не создавать новый.
- Если нет кода: «Где получить код?» → публичная инструкция; в MVP не принимать деньги и не обещать автоматическую выдачу Ozon.
- **Кодовая авторизация и привязка к аккаунту — не одно и то же.** Явное подтверждение передачи кода аккаунту; различать ошибки владения.
- При отказе от ввода кода пользователь может вернуться к анкете, не теряя данные в пределах выбранной модели черновика.

## 7. SCR-05 Создание: последнее подтверждение
- Важно отделить **активацию/выбор доступа** от **необратимого создания заказа**.
- Показать краткий профиль, выбранный доступ и условия использования; чекбокс согласия с версией; финальная кнопка **«Создать мой разбор»**.
- Только финальный POST начинает локальный расчёт, атомарную фиксацию заказа и использование одного доступа после успешного расчёта. Анимация перед этим может быть только декоративной, без ложного статуса генерации.
- Блокировать повторный клик в UI, но главная защита — server-side idempotency key + транзакция/уникальные ограничения в PostgreSQL.
- При ошибке локального расчёта, когда заказ не зафиксирован, доступ не списывать; дать исправить данные.
- Если запрос завершился по таймауту, проверить состояние по idempotency key/ссылке на доступ вместо слепого создания ещё одного заказа.

## 8. SCR-06 Кинематографичное построение
- Two independent state machines: render sequence `intro|orbits|alignment|reveal|done` and server generation `queued|writing|illustrating|ready|failed_retryable|needs_review` (названия уточнить в API).
- Если карта сохранена, отображать её реальные данные. Планеты движутся к положениям, определённым вычислениями, но визуальное расположение — художественная проекция, не притворяющаяся физически точной симуляцией траекторий.
- Режим неизвестного времени не визуализирует вымышленные дома, углы или ложный час рождения.
- Нельзя рисовать fake `%` прогресса ИИ. Показывать реальные этапы: расчёт карты завершён, создаётся текст, иллюстрация, готово.
- При долгом ответе анимация переходит в спокойный ambient loop; не зависает на последнем кадре.
- Skip/reduced motion/offline/refresh поддерживаются. Пропуск сцены не прерывает задание.
- При `needs_review` безопасная остановка, просмотр доступных материалов и ссылка на поддержку; никакого слепого повтора платного вызова.

## 9. SCR-07 Результат
- Hero с персональным заголовком, интерактивная натальная карта, восемь тематических разделов, художественная иллюстрация, скачивание PDF/TXT/PNG.
- Если текст готов, PNG ещё нет: показывать текст/TXT, состояние изображения; PDF после полного набора материалов.
- Повторное открытие не вызывает платные сервисы. Файлы доступны только владельцу права/допустимой кодовой сессии.
- Непривязанному пользователю мягко предложить сохранить результат в почтовом кабинете; действие требует явной привязки кода, не автоматического слияния.

## 10. Ветви и сбои
1. Гость перезагрузил форму → восстанавливаем черновик в рамках согласованного хранения.
2. Гость открыл форму в другом браузере → черновик не переносится без аккаунта; не обещать кросс-девайс восстановление.
3. OTP истёк/SMTP недоступен → вернуться к коду или запросить новый OTP, черновик анкеты не удаляется.
4. Код неверен/заблокирован/чужой → исправить или выбрать другой, без расхода.
5. Код уже использован и принадлежит данной сессии → открыть прежний заказ.
6. Пользователь имеет несколько доступов → явно выбрать один; не смешивать черновики/профили.
7. Ошибка расчёта до фиксации заказа → исправить данные без расхода.
8. Таймаут заказа → recover by idempotency lookup, а не второй расход.
9. Вкладка закрыта во время ИИ → worker продолжает; возвращение по коду/почте открывает реальные статусы.
10. Принят текст, ошибка PNG → текст и карта остаются; продолжение только недостающего этапа при безопасном статусе.
11. Устаревшая сессия → авторизация с возвратом на допустимую страницу; секретные значения не попадут в URL.
12. Пользователь отказался от необязательной аналитики → создание карты работает как обычно.

## 11. Новые задачи на архитектуру относительно старой документации
- Гостевой поиск мест до аутентификации: публичная ограниченная сессия/endpoint, rate limiting.
- Стратегия гостевого черновика и его миграции в подтверждённый доступ; отсутствие гонок и перезаписи чужого черновика.
- Новый маршрут `/create/*` без кода; API для профиля по-прежнему не разрешает создавать оплаченный заказ без доступа.
- Восстановление процесса после OTP со сохранением профиля без помещения персональных данных в query string.
- Согласование приватности: минимизация хранения данных рождения, сроки жизни незавершённых черновиков, без отправки в аналитику.
- Отдельная операция привязки и расхода доступа; транзакции/идемпотентность.

## 12. Приёмочные критерии (основа E2E)
- `E2E-01`: `/` CTA → анкета без кода и email; 4 шага, возврат не теряет поля.
- `E2E-02`: выбранный город хранит city_id; редактирование текста сбрасывает выбор.
- `E2E-03`: подтверждение показывает корректный профиль; редактирование возвращает с сохранением.
- `E2E-04`: без действующего кода/доступа создать заказ невозможно.
- `E2E-05`: email OTP после анкеты не уничтожает введённые данные.
- `E2E-06`: валидный новый код → финальное согласие → один заказ, один расход.
- `E2E-07`: двойной клик, сетевой retry и две вкладки не создают второй заказ по тому же доступу.
- `E2E-08`: использованный код не создаёт второй заказ; при разрешённом владении открывает старый.
- `E2E-09`: unknown birth time → никаких вымышленных домов/ASC, корректная визуальная сцена.
- `E2E-10`: refresh/close во время генерации → возвращается реальное состояние.
- `E2E-11`: при частично готовом результате ранее завершённые этапы не запускаются заново.
- `E2E-12`: доступ с чужой сессией к заказу и скачиванию запрещён.
- `E2E-13`: mobile/reduced-motion/keyboard функционируют.
