# SCR-04 — Доступ

Срез: 5 (кодовая ветка). Маршрут: `/create/access`. Композиция сцены: `access` должна совпасть с `review` без перелёта камеры (Р-A2); сейчас ещё равна `hero`, меняется на стадии интерфейса.

Статус: **стадия 0 утверждена владельцем 12.11.2026 (Р-A1 – Р-A12). Этап API и моков завершён 12.11.2026** (Ж1): контракт `0.3.0-5`, MSW-моки, 37 unit-тестов, ARCH §9.1 и §15.3 синхронизированы. Интерфейс `AccessView` и M05 реализованы на моках 12.11.2026 (Ж3). **Визуал desktop/mobile и основные переходы утверждены владельцем 12.11.2026** (Р-A13); техническая приёмка — Ж4.

### 0.1. Требования

1. Заголовок не обещает, что карта рассчитана: «Данные заполнены. Остался доступ к персональному разбору» (SCREEN_SPEC §6, M05).
2. Поле кода и проверка. Неверный, заблокированный, лимит, чужая привязка — без утечки деталей (§6, ARCH §10.3).
3. Использованный код: «По этому коду уже создан разбор», открыть его при допустимой сессии, ввести другой код; новый заказ не создаётся (§6, §1, §10 п. 5).
4. Нет кода: «Где получить код?» → публичная информация; без оплаты и без обещаний автоматической выдачи через Ozon (§6, §1).
5. Отказ от ввода кода: возврат к анкете без потери данных (§6).
6. Ввод кода не создаёт заказ и не расходует доступ (А7, ARCH §10.3: кодовый вход — «Расход? Нет»).
7. Ошибки — рядом с полем, без тряски сцены; серверные ограничения не подменяются анимацией (M05).
8. Код не попадает в URL, `sessionStorage`, `localStorage`, аналитику и логи клиента; в Git и тестах — только синтетические строки (AGENTS.md, ARCH §26).
9. Существующая кодовая сессия не заменяется без явного выбора пользователя (А8).

### 0.2. Пользовательский путь

```
SCR-03 «Продолжить» (проверка 200 по актуальной анкете)
        │
        ▼
/create/access ── guard: анкета полная и отпечаток проверки совпадает? ── нет ──▶ /create/review (повторная проверка, Р5)
        │ да
        ▼
GET /session ─┬─ аноним ─────────────▶ Ввод кода
              ├─ code, available ───▶ «Код принят» (существующая сессия)
              └─ code, consumed ────▶ «По этому коду уже создан разбор»

Ввод кода ── «Проверить код» ── POST /auth/code
        ├─ 200 available ─▶ «Код принят» ── «Продолжить» ─▶ /create/consent
        ├─ 200 consumed ──▶ «По этому коду уже создан разбор» ─ «Открыть разбор» ─▶ /orders/:id
        │                                                     └ «Ввести другой код» ─▶ Ввод кода (замена, §0.6)
        ├─ 422 code_malformed / code_invalid ─▶ ошибка у поля, ввод сохранён
        ├─ 403 code_bound_to_account ─────────▶ ошибка у поля «войди по почте» (C-A2)
        ├─ 409 session_conflict ──────────────▶ выбор: заменить / оставить текущий (§0.6)
        ├─ 429 rate_limited ──────────────────▶ сообщение, повтор позже
        └─ 5xx / сеть / 400 ──────────────────▶ сбой, повтор вручную

«← Назад» ─▶ /create/review (анкета на месте, повторная проверка по Р5)
«Где получить код?» ─▶ /natal-chart, когда SCR-11 готов; до этого неактивный текст (§0.7)
```

Сценарии по типу кода (ARCH §10.3):

| Код | Ответ сервера | Сессия | Что видит пользователь | Действия |
|---|---|---|---|---|
| Свободный (`available`, не привязан) | 200, `entitlement.state = available` | Выдаётся кодовая | «Код ••••7K2Q принят.» | «Продолжить» → `/create/consent`; «Использовать другой код» |
| Не разбирается как код 2.0 | 422 `code_malformed` | Нет, текущая не меняется | Текст ошибки с подсказкой о старом сайте (C-A3) | Исправить ввод |
| Неизвестный / не выпущен / заблокирован / не тот продукт | 422 `code_invalid` (единый ответ) | Нет | «Этот код не подходит…» | Исправить ввод |
| Использованный (`consumed`, не привязан) | 200, `state = consumed`, `order_id` | Выдаётся кодовая | «По этому коду уже создан разбор.» | «Открыть разбор» → `/orders/:id`; «Ввести другой код». Анкета не трогается |
| Привязан к аккаунту | 403 `code_bound_to_account` | Нет | «Этот код привязан к кабинету. Войди по почте…» | Исправить ввод (C-A2) |

Ни один ответ не создаёт заказ и не меняет состояние доступа (А7).

### 0.3. Контракт (утверждён, Р-A6; в `api/openapi.yaml` с версии `0.3.0-5`)

Общие правила — ARCH §15.1: `application/json`, неизвестные поля отклоняются, ошибки `application/problem+json` с `code` и `detail` на русском, `Cache-Control: no-store`, проверка `Origin` для небезопасных методов (§9.4). Cookie `__Host-lk_sid` (`HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`), срок кодовой сессии — по Q2 (предложено 7 дней).

**`POST /api/v1/auth/code`** — `operationId: startCodeSession`, Public, лимиты на IP и глобально (ARCH, «Перебор кодов»).

Запрос `CodeLogin`:

| Поле | Правило |
|---|---|
| `code` | Строка 1–64 символа как введена; нормализацию (регистр, пробелы, дефисы, похожие символы) и проверку контрольного символа делает сервер (§10.1) |
| `replace_session` | `boolean`, необязательно; отсутствие равно `false`. `true` — пользователь явно согласился заменить текущую сессию (§0.6). В схеме без `default`, иначе генератор делает поле обязательным в TS |

Ответы:

| Статус | `code` | Тело / смысл |
|---|---|---|
| 200 | — | `Session` (вариант `code`, ниже) + `Set-Cookie`. Для использованного кода — тот же ответ с `state = consumed` и `order_id` |
| 400 | `validation_failed` | Тело не разобрано: не JSON, нет `code`, неизвестные поля |
| 422 | `code_malformed` | Ввод не разбирается как код 2.0; `detail` — подсказка о старом сайте (§26 п. 2) |
| 422 | `code_invalid` | Единый ответ без деталей |
| 403 | `code_bound_to_account` | Доступ привязан к аккаунту |
| 409 | `session_conflict` | **Новый код ошибки (C-A5).** У запроса есть действующая сессия другого доступа, а `replace_session` не `true`. Текущая сессия не меняется |
| 429 | `rate_limited` | Лимит попыток; заголовок `Retry-After` в секундах |
| default | `internal_error` и др. | Сбой |

Повтор того же кода при действующей сессии **того же** доступа — 200 без конфликта (идемпотентно).

**`GET /api/v1/session`** — `operationId: getSession`, любой посетитель, всегда 200:

```
Session = AnonymousSession | CodeSession            (дискриминатор principal)
  AnonymousSession { principal: "anonymous" }
  CodeSession      { principal: "code", expires_at: date-time, entitlement: CodeEntitlement }
CodeEntitlement = Available | Consumed              (дискриминатор state)
  CodeEntitlementAvailable { id: uuid, state: "available", code_mask: CodeMask }
  CodeEntitlementConsumed  { id: uuid, state: "consumed",  code_mask: CodeMask, order_id: uuid }
CodeMask = последние 4 символа нормализованного кода (ARCH §10.2), ^[0-9A-HJKMNP-TV-Z]{4}$
```

`POST /auth/code` отвечает 200 схемой `CodeSession`. `order_id` приходит только вместе с действующей кодовой сессией этого доступа; открыть заказ можно только с ней (Р-A10, ARCH §9.5).

Вариант `account` добавляется в срезе 7. Код целиком никогда не возвращается. Заблокированный доступ делает кодовую сессию недействительной (§9.2) — ответ `anonymous`.

**Не нужны в срезе 5:** `DELETE /session` (замена идёт через `replace_session`; выход — срез 7), `GET /entitlements*`, `/entitlements/claims`, `/entitlements/{id}/draft`, `/auth/email/*`.

**Моки** — Ж1.

### 0.4. Результат проверки анкеты (А5, А6)

Сейчас признак проверки нигде не хранится: SCR-03 проверяет анкету при каждом входе (Р5) и держит результат только в памяти экрана.

**Решение (Р-A7) — отпечаток проверенной анкеты в `sessionStorage`.**

- Ключ `cosmos.intake.check.v1`, значение `{version: 1, fingerprint, checkedAt}`. Та же вкладка и тот же срок жизни, что у черновика `cosmos.intake.v1` (24 часа). В URL, аналитику и логи не попадает.
- `fingerprint` — SHA-256 (hex, `crypto.subtle.digest`) канонического JSON тела запроса `profile-checks`: `toProfile(draft)` с фиксированным порядком ключей (`name` уже без пробелов по краям). Копия анкеты под видом отпечатка не хранится. Guard поэтому асинхронный (vue-router это допускает).
- **Запись:** SCR-03 после ответа 200 сохраняет отпечаток **отправленного** тела. При старте каждой проверки (Р5) прежний отпечаток удаляется.
- **Инвалидация без наблюдателей:** guard сравнивает сохранённый отпечаток с `toProfile(текущий черновик)`. Любая правка имени, даты, места, времени, источника или точности даёт другой отпечаток — проверка считается недействительной (А6). `reset()` черновика удаляет и отпечаток. Истёк срок — недействителен.
- **Guard `/create/access`:** неполная анкета → как guard review (первый незаполненный шаг с флагом редактирования); полная, но отпечатка нет или он не совпадает → `replace` на `/create/review` (там пройдёт новая проверка); совпадает → экран. Guard без сети; сессию читает сам экран.
- Сервер всё равно повторно валидирует анкету при создании заказа (ARCH §8.3 п. 4); отпечаток — только навигационное правило, не защита.

Это требует минимальной правки кода SCR-03 (запись и сброс отпечатка в `review.ts` / `ReviewView.vue`, сброс в `draft.ts`) без изменения его вида и поведения — см. C-A6.

### 0.6. Существующая кодовая сессия (А8)

Сессия — cookie на весь браузер, черновик — на вкладку. Поэтому на SCR-04 может прийти посетитель, у которого уже открыт код (в этой или другой вкладке).

1. **При входе** экран читает `GET /session`. Есть кодовая сессия → вместо поля показывается её состояние: «Код ••••7K2Q уже принят.» (или «По коду ••••7K2Q уже создан разбор.»). Новый код не запрашивается (SCREEN_SPEC §1, «не требовать новый код»).
2. **Явная замена.** «Использовать другой код» / «Ввести другой код» раскрывает поле с заметкой под ним: «Код ••••7K2Q закроется в этом браузере. Его можно будет ввести снова.» и ссылкой «Отмена» (возврат к принятому коду). Отправка из этого режима идёт с `replace_session: true`. Нажатие ссылки и видимая заметка — и есть явный выбор.
3. **Защита на сервере.** Без `replace_session: true` при действующей сессии другого доступа сервер отвечает 409 и сессию не трогает. Это закрывает гонки: вторая вкладка, сбой `GET /session`, сессия, открытая после входа на экран.
4. **409 на экране:** строка у поля «В этом браузере уже открыт другой код (••••7K2Q).» и две кнопки: «Заменить» (повтор с `replace_session: true`) и «Оставить текущий» (показать принятый код). Маска берётся из повторного `GET /session`.
5. Тот же код при той же сессии — 200, без вопросов.

Замена сессии не расходует и не отвязывает ни один доступ: прежний код остаётся действующим (ARCH §10.3).

### 0.7. «Где получить код?» (А10)

Отдельной публичной инструкции в реестре SCREEN_SPEC §2 нет. Существующие маршруты (`app/routes.ts`), все пока заглушки среза 11:

| Маршрут | Экран | Пригодность |
|---|---|---|
| `/support` | SCR-13 «Контакты поддержки» | Можно спросить, где взять код; ARCH §26 п. 3 уже кладёт туда пункт про старые коды |
| `/natal-chart` | SCR-11 «Информация об услуге» (CTA: начать, пример, активация) | Ближе к «публичной инструкции», но содержание о получении кода в спецификации не задано |
| `/example` | SCR-12 «Пример разбора» | Не про получение кода |

**Решение (Р-A3):** целевой адрес — `/natal-chart`, там будет объясняться приобретение кода. Пока SCR-11 — заглушка, активной ссылки нет: на месте ссылки — неинтерактивный текст «Где получить код? Расскажем на странице о натальной карте — она скоро появится.» (предложение текста). Когда SCR-11 будет готов, текст станет ссылкой в той же вкладке (черновик вкладки сохранится). Новую страницу не создаём.

### 0.8. Визуальная спецификация

**Идея.** На SCR-03 анкета была закончена. SCR-04 — тихая пауза перед последним шагом: одна строка ввода на том же подчёркивании и в том же кегле, что ответы анкеты. Ни карточки, ни рамки, ни «замка». Активация не празднуется: принятый код — спокойная строка с золотой отметкой, как «Данные проверены» на SCR-03.

**Токены — только существующие** (DESIGN_SYSTEM §4, `ui/tokens.css`).

| Роль | Токен |
|---|---|
| Фон, сцена | `--cosmos-bg`, кадр `access` (C-A1) |
| Ввод кода | `--cosmos-text`, шрифт поля SCR-02, `letter-spacing` как у подписи `Field` |
| Подпись поля, подсказка | `--cosmos-muted` / `--cosmos-faint` |

**Тексты** (предложение, утверждает владелец — П-A1; обращение на «ты», как SCR-02/03):

- Заголовок: «Данные заполнены.» / «Остался доступ к персональному разбору.» (строка 2 — золотая italic serif; текст из SCREEN_SPEC §6).

### 0.11. Стабильность компоновки

- Слот формы имеет высоту поля с первого кадра, в том числе пока читается сессия: строки «принят» и «уже создан» занимают ту же высоту, кнопки не прыгают.
- Ошибка **заменяет** подсказку под линией; длинная ошибка растит только свой блок.
- Строка статуса — под кнопками, как SCR-03; меняется только её содержимое.
- Строка конфликта заменяет подсказку; кнопки «Заменить / Оставить текущий» встают в слот подсказки, основная кнопка остаётся на месте.

### 0.12. Фокус и клавиатура

| Событие | Фокус |

| Ошибка у поля (422 / 403 / пусто) | Остаётся в поле; текст связан `aria-describedby`, поле `aria-invalid="true"`; объявляет строка статуса (`role="status"`, `aria-live="polite"`) |
| 200 `available` | На «Продолжить» |
| 200 `consumed` | На «Открыть разбор» |
| 409 | На «Заменить» |
| «Использовать другой код» / «Ввести другой код» | В поле |
| «Отмена» / «Оставить текущий» | На «Продолжить» (или «Открыть разбор») |

### 0.14. Критерии приёмки

**Функциональные**

- Guard (А5, А6): без отпечатка → `/create/review`; правка любого поля анкеты после проверки → `/create/review`; неполная анкета → первый незаполненный шаг; после 200 на review → экран открывается.
- Каждое состояние §0.5 воспроизводится моком; тексты по §0.8.
- А7 / E2E-04 (часть): ни одно действие на SCR-04 не шлёт `POST /orders` и запросов расхода доступа; «Продолжить» лишь переходит на `/create/consent`.
- А8: при кодовой сессии экран показывает её, а не поле; запрос с `replace_session: true` уходит только после «Использовать / Ввести другой код» или «Заменить»; при 409 сессия не меняется до выбора.
- Код не появляется в URL, `sessionStorage`, `localStorage`, консоли; после успеха поле очищено.
- MOT-03: ошибка не стирает ввод, нет мерцаний и прыжков фокуса.
- Двойное нажатие «Проверить код» — один запрос; автоповторов нет.
- «← Назад» возвращает на review с сохранённой анкетой; «Где получить код?» — не ссылка и никуда не ведёт, пока SCR-11 не готов.
- Контракт: мок типизирован сгенерированной схемой, `make check-gen` чистый, `contract_test.go` валидирует спецификацию.
- axe без нарушений во всех состояниях; клавиатурный проход; reduced motion; без WebGL.

**Визуальные** (`make visual`, `?scene=freeze`): 1440×900, 1920×1080, 768×1024, 390×844, 375×667 — ввод, ввод с клавиатурой (mobile), проверка (`?auth-code=slow`), принят, уже создан, каждая ошибка, конфликт, лимит, сбой, существующая сессия, reduced motion. Колонка не заходит на планету, нет горизонтальной прокрутки, кнопки и ошибки не обрезаны, ошибок консоли нет. Утверждение владельцем по снимкам.

## 2. Хореография (план стадии 2, M05)

Токены SCR-02 §2.1, новых нет: `stepEnter` 420 мс `out`, `stepExit` 200 мс, `micro` 160 мс, `cinematic` для камеры.

**Вход с SCR-03 («Продолжить»)**

| Время | DOM | Сцена |
|---|---|---|
| 0 мс | `push('/create/access')`, фокус по §0.12. `GET /session` уходит сразу | Перелёт в кадр `access` — зависит от C-A1 |
| 0–200 мс | Колонка review уходит влево (описано в SCR-03 §2) | — |
| 80–500 мс | Колонка SCR-04 приходит справа одним слоем: opacity, сдвиг 20→0, blur 2→0, 420 мс, `out`. Слот формы зарезервирован | — |
| ≥ 300 мс | Если сессия ещё не прочитана — строка «Проверяем доступ…» (opacity 160 мс) | — |

**Смена состояний**

- Фокус в поле: подчёркивание `--cosmos-line` → `--cosmos-gold`, 160 мс.
- Проверка кода: после 300 мс — кнопка opacity 0.5, бегущая линия (`transform`), как SCR-03.
- Ошибка: подсказка гаснет 120 мс, ошибка появляется (opacity, сдвиг −4→0, 160 мс), линия → `--cosmos-danger` 160 мс. Без тряски поля и сцены (M05).
- Принят: поле и строка «принят» меняются кроссфейдом 160 мс на месте; линия прорисовывается золотом (`scaleX` 0→1, 300 мс, `out`) и остывает до `--cosmos-line` (400 мс) — тот же акцент, что M04. Сцена не реагирует: активация не изображает создание карты (M05).
- Уже создан, конфликт, замена: кроссфейд 160 мс в слоте формы.

**Выход.** «Продолжить» и «Открыть разбор» — колонка уходит влево (200 мс). «← Назад» — вправо (200 мс), review приходит слева.

**Reduced motion.** Колонка — opacity 200 мс, уход 120 мс; без сдвигов, blur и прорисовки линии; бегущая линия → статичный текст. Перелёт камеры не выполняется (MOTION §5).

**Без WebGL.** Постер; форма работает полностью.

## Журнал реализации

**Ж1. Контракт и моки.**

- `api/openapi.yaml` → `0.3.0-5`: тег `auth`; `GET /api/v1/session` (`getSession`); `POST /api/v1/auth/code` (`startCodeSession`) с ответами 200 / 400 / 403 / 409 / 422 / 429 (`Retry-After`) / default; схемы `CodeLogin`, `Session`, `AnonymousSession`, `CodeSession`, `CodeEntitlement` (+ `Available` / `Consumed`), `CodeMask`; `session_conflict` в `ErrorCode`. Типы — `make gen`.
- `frontend/src/mocks/access.ts`: нормализация кода (регистр, пробелы, дефисы, O→0, I/L→1; префикс `LK`, алфавит, 25 символов; контрольный символ не вычисляется — алгоритм сервера), синтетический реестр, сессия в памяти, правила замены (тот же доступ — 200 без конфликта; другой без `replace_session: true` — 409; любая ошибка и лимит сохраняют прежнюю сессию; истёкшая сессия не мешает), лимит 5 неудачных попыток за 60 с (409 и успехи не считаются).
- Синтетические коды (`syntheticCodes`): `LK-FREE0-…-0F001` и `…-0F002` — свободные, `LK-SPENT-…-0S001` — использован, `LK-ACCT0-…-0A001` — привязан к аккаунту, `LK-DENY0-…-0D001` — заблокирован, `LK-ZZZZZ-…-0Z001` — правильной формы, но неизвестен. Любая строка без `LK` или неверной длины — `code_malformed`.
- `frontend/src/mocks/handlers.ts`: обработчики `GET /session` и `POST /auth/code`; переключатели `?session=code-available|code-consumed|slow|error`, `?auth-code=slow|error|rate-limited`; `problem()` принимает заголовки.
- `frontend/src/main.ts`: MSW-воркер запускается с `quiet: true` — иначе он печатает в консоль тела запросов, в том числе код.
- Тесты `frontend/src/mocks/access.spec.ts` (37): нормализация; все ответы кода; 400 по форме тела; повтор того же кода; конфликт без согласия и замена с согласием; сохранение сессии при каждой ошибке и при лимите; лимит, `Retry-After` и повтор после окна; коды не попадают ни в один ответ; через MSW — сессия после входа, 409 как `problem+json`, `Retry-After`, отсутствие вывода в консоль; все коды соответствуют синтетическому шаблону.
