# SCR-05 — Подтверждение согласия

Срез: 6 (создание заказа). Маршрут: `/create/consent`. Композиция сцены: `access` (= кадр `review`), без перелёта камеры (К12).

Статус: **стадия 0 подготовлена 16.11.2026; визуальная концепция и каркасы утверждены владельцем (Р-C1).** **Этап 1 «контракт и MSW-моки» завершён 16.11.2026** (Ж1): контракт `0.3.0-6`, `POST /api/v1/orders`, `PublicConfig.consent_version` / `legal_ready`, мок создания заказа и тесты. **Этап 2 «интерфейс на моках» реализован 16.11.2026** (Ж2): `ConsentView`, `consent.ts`, guard маршрута; решения владельца Р-C8–Р-C12 внесены в журнал. **Техническая приёмка проведена 16.11.2026** (Ж3): адресные E2E, production-прогон, axe, клавиатура, reduced motion, защита от двойного создания, восстановление после неизвестного исхода; **визуал и UX экрана утверждены владельцем без правок (Р-C13).** Юридические формулировки не утверждены (Q12) и в этом документе не придумываются; реальное создание заказа остаётся закрытым (Р-C10), SCR-05 принят как интерфейс на моках.

### 0.1. Требования

1. Экран — последнее подтверждение: пользователь видит, что именно будет создано и что будет использован один доступ (К1, К7, SCREEN_SPEC §7).
2. Показываются краткая сводка анкеты и маска выбранного кода (К2). Полный код нигде не показывается и не хранится на клиенте (SCR-04 §0.1 п. 8).
3. Чекбокс согласия не отмечен по умолчанию, не запоминается и сбрасывается при каждом входе и при смене версии согласия. Без отметки «Создать мой разбор» неактивна.
4. Версию согласия клиент берёт из `PublicConfig.consent_version` (К9) и отправляет её в `POST /orders`. Клиентская копия текста согласия не фиксирует версию сама по себе: сервер проверяет актуальность.
5. Пока Q12 открыт, реальный `POST /orders` не отправляется ни при каких действиях пользователя (К6). Блокировка действует «по умолчанию закрыто»: если состояние неизвестно, создание недоступно.
6. Экран не обещает готовность результата до подтверждённого ответа API (M06). Успешная постановка в очередь не называется «разбор готов» и не показывается как завершение (К13).
7. Один доступ — максимум один заказ: защита от двойного создания на клиенте (одна отправка, один ключ) и на сервере (идемпотентность, транзакция; ARCH §11).
8. Неизвестный исход запроса сначала восстанавливается чтением состояния, а не новым созданием (M06, SCREEN_SPEC §7).
9. Назад — на `/create/access` без потери анкеты и сессии (К8).
10. При `features.generation=false` создание недоступно с понятным сообщением (К11).
11. Ошибки не стирают данные и не двигают сцену (MOT-03). Текст ошибок — рядом с кнопкой, без модальных окон.
12. Токены, компоненты и типографика — как SCR-03/04; новых цветов и шрифтов нет.

### 0.2. Пользовательский путь

```
SCR-04 «Продолжить» (код принят, доступ available)
        │
        ▼
/create/consent ── синхронные guard: анкета полная? отпечаток проверки жив? ── нет ──▶ шаг анкеты / /create/review
        │ да
        ▼
GET /session + GET /config
   ├─ аноним / сессия истекла ───────────────▶ replace /create/access (анкета сохранена)
   ├─ code, entitlement.state = consumed ────▶ replace /orders/:order_id (заказ уже есть)
   ├─ ошибка чтения сессии/конфигурации ─────▶ состояние «не удалось проверить» (создание недоступно)
   └─ code, available ──┐
                        ▼
        creation_mode (§0.5):
          blocked  ─▶ сводка видна, «Создать мой разбор» неактивна, сообщение
          off      ─▶ features.generation=false: сообщение (К11)
          test     ─▶ только стенд с моками: баннер «тестовый режим», полный сценарий
          live     ─▶ (после Q12) обычный сценарий
                        ▼
        отметить согласие ─▶ «Создать мой разбор»
                        ▼
        POST /orders (Idempotency-Key) ── 201 / 200 ──▶ очистить черновик и ключ ─▶ /orders/:id/creating
                        │
                        ├─ определённая ошибка (4xx) ─▶ текст у кнопки, данные сохранены
                        └─ неизвестный исход (сеть/таймаут/5xx) ─▶ восстановление по GET /session ─▶ order_id найден → SCR-06
                                                                       └─ не найден → «Проверить ещё раз» (тот же ключ)
```

«← Назад» из любого состояния, кроме `submitting` и `recovering`: `push('/create/access')`. На SCR-04 существующая кодовая сессия показывается как «Код принят» (SCR-04 §0.6), поэтому возврат не требует повторного ввода кода.

### 0.3. Guard

Маршрутный guard остаётся синхронным и дешёвым, как `guardAccess`; сетевая часть — в самом экране (как чтение сессии на SCR-04), чтобы не блокировать навигацию.

| # | Проверка | Где | Если не выполнена |
|---|---|---|---|
| 1 | Анкета полная (`guardIntake`) | router, sync | Первый незаполненный шаг, `from=review` |
| 2 | Отпечаток проверки жив и совпадает с анкетой (SCR-04 §0.4, Р-A7) | router, sync | `replace` на `/create/review` |
| 3 | `GET /session`: принципал `code`, сессия не истекла | экран, async | `replace` на `/create/access`; анкета и отпечаток сохраняются |
| 4 | `entitlement.state = available` | экран, async | `consumed` → `replace` на `/orders/:order_id` (Р-A10); иначе `/create/access` |
| 5 | `GET /config` прочитан | экран, async | Состояние «не удалось проверить»; создание недоступно, «Проверить ещё раз» |

- Выбранный доступ — это `entitlement.id` текущей кодовой сессии. Отдельного клиентского хранилища «выбранного доступа» нет и не вводится (SCR-04 Р-A5); ARCH §26 «анкета + выбранный доступ» исполняется так (см. C-C4).
- Guard выполняется при входе. Если отпечаток истёк (24 ч) или сессия закончилась уже на экране, открытая форма не ломается: сервер повторно проверяет всё при `POST /orders`; клиент разбирает ответ (§0.8).
- Если пока читается сессия, сводка берётся из черновика синхронно, блок подтверждения резервирует высоту (§0.11); «Создать мой разбор» неактивна, статус «Проверяем доступ…» после 300 мс.
- Guard не пишет в хранилище и не расходует доступ.

### 0.4. Состояния

| Состояние | Условие | Что видит пользователь |
|---|---|---|
| `checking` | читаются сессия и конфигурация | Сводка из черновика, блок подтверждения зарезервирован; «Создать мой разбор» неактивна; статус «Проверяем доступ…» (после 300 мс) |
| `ready` | `available`, режим `live`/`test`, чекбокс не отмечен | Все блоки; кнопка `aria-disabled`, причина связана `aria-describedby` |
| `ready_checked` | чекбокс отмечен | Кнопка активна (кроссфейд 160 мс) |
| `submitting` | запрос в пути | Чекбокс, «Изменить» и «Назад» неактивны (`aria-disabled`); кнопка 0.5 и бегущая линия (после 300 мс); статус «Создаём заказ…»; камера и сцена не реагируют |
| `recovering` | исход запроса неизвестен | Управление заблокировано; статус «Проверяем, создан ли заказ…»; один запрос `GET /session` (без побочных эффектов) |
| `unknown` | восстановление не дало ответа | Текст у кнопки (§0.8); «Проверить ещё раз» повторяет `POST /orders` с **тем же** ключом |
| `blocked` | режим `blocked` (Q12 открыт) | Сводка и блок расхода видны; чекбокса нет; кнопка `aria-disabled`; нейтральное сообщение «Создание разбора пока недоступно.» (предложение) |
| `generation_off` | `features.generation=false` | То же, что `blocked`, другой внутренний код; сообщение по К11 (предложение §0.9) |
| `config_error` | `GET /config` или сессия недоступны | «Не удалось проверить условия создания. Проверь соединение и попробуй ещё раз.»; создание недоступно; «Проверить ещё раз» |
| `consent_outdated` | `409 consent_outdated` | Чекбокс сбрасывается, версия перечитывается, фокус на чекбокс; сообщение (§0.8) |
| `entitlement_used` | `409 entitlement_used` | «По этому доступу уже создан разбор.» Кнопка «Открыть разбор» (`order_id` из `GET /session`) |
| `error` | остальные определённые ошибки | Сообщение у кнопки, данные сохранены, повтор — той же кнопкой |
| `test` | режим `test` (только стенд) | Постоянный баннер тестового режима (§0.5); остальное как `ready` |

### 0.5. Режимы создания и блокировка до Q12 (Предложение)

`creation_mode` вычисляется на клиенте из двух независимых условий и всегда «по умолчанию закрыто»:

| Режим | Когда | Отправляется ли реальный `POST /orders` |
|---|---|---|
| `blocked` | юридический допуск не подтверждён (Q12 открыт) | Нет. Обработчик кнопки не имеет пути к запросу |
| `generation_off` | `features.generation = false` | Нет |
| `test` | явный тестовый режим: только в сборке со стендом MSW (`mocks` включены), включается переключателем на стенде, а не пользовательским действием в рабочей сборке | Только на мок; запрос уходит в MSW |
| `live` | юридический допуск подтверждён **и** генерация включена | Да (после Q12 и backend) |

Правила:

1. Признак юридического допуска не выводится из версии согласия: `consent_version` есть и у тестового мока. Признак — `PublicConfig.legal_ready` (по умолчанию `false`, Р-C2); backend независимо проверяет его в `POST /orders` (`403 creation_unavailable`). Клиентский флаг не заменяет серверную проверку.
2. Тестовый режим невозможен в рабочей сборке: код режима исключается сборкой по `import.meta.env`, а не скрывается стилями. Проверка в приёмке: в production-бандле нет строки тестового режима и переключателя.
3. В тестовом режиме экран всегда показывает заметный баннер «Тестовый режим. Заказ создаётся на моке, юридический текст не утверждён» (предложение, не юридический текст) и вместо юридической формулировки у чекбокса — явная заглушка «[Текст согласия появится после Q12]». Заглушка не должна выглядеть как настоящий текст.
4. Снимки и E2E тестового режима всегда помечены; снимок без баннера означает режим `blocked` или `live`.
5. Пока Q12 открыт, по умолчанию (E2E без тестового режима) тест гарантирует: ни одно действие на экране не шлёт `POST /orders`.

### 0.6. `POST /api/v1/orders` (в `api/openapi.yaml` с версии `0.3.0-6`)

Ниже — исходные пожелания экрана (стадия 0). **Утверждённый контракт — в `api/openapi.yaml`, итоги и отличия — в Ж1.** Главные отличия от первоначальной таблицы: 403 `creation_unavailable` (определённый отказ, не неизвестный исход), 404 `not_found` для чужого `entitlement_id`, `consent_version` входит в отпечаток идемпотентности, 201/200 — `{id, status: queued}`.

| Элемент | Значение |
|---|---|
| Запрос | `POST /api/v1/orders`; заголовок `Idempotency-Key` (16–80 символов `[A-Za-z0-9_-]`); защита изменяющих запросов — как у остальных (ARCH §9.4) |
| Тело | `{entitlement_id, profile, consent_version}` (ARCH §11.1). `profile` — результат `toProfile` из черновика; координаты и часовой пояс сервер берёт по `place_id` |
| 201 | Новый заказ; экрану нужен только `id` и признак статуса постановки (`queued`) — **не** «готово» |
| 200 | Тот же заказ при повторе того же ключа или совпавшей анкете (ARCH §11.3) |
| 400 | Невалидное тело / заголовок |
| 401 | `unauthenticated` — сессия закончилась |
| 409 | `consent_outdated`; `entitlement_used`; `entitlement_blocked`; `idempotency_key_reused` |
| 422 | `validation_failed`, `place_not_found`, `birth_time_nonexistent`, `birth_time_ambiguous`, `calculation_failed` — доступ остаётся `available` |
| 429 | `rate_limited`, `Retry-After` |
| 5xx / сеть | неизвестный исход (§0.7) |
| Для блокировки | Нужен код для «создание сейчас недоступно» (Q12 / генерация выключена). Кода в каталоге ARCH §15.3 нет — вопрос В-2 |

Принципы:

- В ответе нет самого текста согласия и нет данных клиента сверх заказа.
- Время принятия согласия фиксирует сервер (`consent_accepted_at`, модель `orders` в ARCH); клиентское время не отправляется.
- В ответе экрану не нужна полная схема `Order`: её определят SCR-06/07; экран берёт `id`.
- Тело запроса и ключ не пишутся в консоль, URL и аналитику.

### 0.7. Идемпотентность и восстановление после неизвестного исхода

**Ключ.** Генерируется при первом входе на экран в состоянии `ready` и хранится в `sessionStorage` под `cosmos.order.attempt.v1`: `{key, entitlementId, fingerprint, consentVersion, createdAt}` (ARCH §11.1: «ключ хранится рядом с fingerprint черновика»). Значение `fingerprint` — отпечаток проверки SCR-03 (Р-A7). Формат ключа — `crypto.randomUUID()` (36 символов, подходит под 16–80). В хранилище нет кода доступа и данных анкеты.

**Правила ключа**

| Событие | Ключ |
|---|---|
| Повторный вход при тех же `entitlement_id` и `fingerprint` | Сохраняется |
| Анкета изменена (новый отпечаток) или другой доступ | Создаётся заново |
| `consent_outdated` (заказ не создан) | Создаётся заново |
| Повтор после неизвестного исхода | Тот же |
| Определённая ошибка 4xx без изменения данных | Тот же |
| Успех (201/200) | Удаляется вместе с черновиком и отпечатком (ARCH §8.3 п. 4) |

**Неизвестный исход** (сеть, таймаут, 5xx без тела `problem+json`, обрыв):

1. Экран входит в `recovering`; повторной отправки нет.
2. Один запрос `GET /api/v1/session` (в контракте есть). Если `entitlement.state = consumed` → `order_id` найден, дальше как при успехе. Отдельный `GET /entitlements/{id}` для кодовой ветки не нужен (он нужен только аккаунтной ветке, срез 7).
3. Если доступ всё ещё `available` или сессию прочитать не удалось → состояние `unknown`: «Не удалось получить ответ. Заказ мог быть создан. Проверь ещё раз — второй заказ не появится.» (предложение) и «Проверить ещё раз». Кнопка повторяет `POST /orders` с **тем же** ключом: по ARCH §11.3 результат — 200 с тем же заказом либо 201, если первый запрос не дошёл. Автоповторов нет.
4. Новый ключ при неизвестном исходе не создаётся никогда.

### 0.8. Ошибки и защита от двойного создания

**Защита.** Клиент: один запрос на нажатие, кнопка и остальное управление неактивны в `submitting`/`recovering`, повторное нажатие (мышь, Enter, Space, двойной тап) игнорируется. Сервер (ARCH §11): ключ, `UNIQUE(idempotency_scope, key)`, блокировка доступа `FOR UPDATE`, заказ по `entitlement_id`. Главная защита — серверная; клиентская лишь не создаёт шума.

**Ошибки** (тексты — предложение; текст сервера `detail` показывается, если он есть и не раскрывает деталей):

| Ответ | Поведение | Текст (предложение) |
|---|---|---|
| 401 `unauthenticated` | `replace` на `/create/access`, анкета и отпечаток сохранены | Без текста на SCR-05; на SCR-04 — состояние ввода кода |
| 409 `consent_outdated` | Сброс чекбокса, перечитать `GET /config`, новый ключ, фокус на чекбокс | «Условия обновились. Отметь согласие ещё раз.» |
| 409 `entitlement_used` | `GET /session` → `order_id`; кнопка «Открыть разбор» | «По этому доступу уже создан разбор.» |
| 409 `entitlement_blocked` | Создание невозможно, данные сохранены | «Этот код сейчас недоступен. Напиши в поддержку.» (ссылка на поддержку неактивна до SCR-13, как «Где получить код?») |
| 409 `idempotency_key_reused` | Клиентская ошибка: новый ключ, повтор один раз вручную | «Не удалось создать заказ. Попробуй ещё раз.» |
| 422 `validation_failed` / `place_not_found` / `birth_time_*` | «Проверить и изменить» → `/create/review`; доступ не потрачен | `detail` сервера или «Нужно поправить данные анкеты.» |
| 422 `calculation_failed` | Данные сохранены; повтор разрешён; доступ не потрачен | «Не удалось рассчитать карту. Доступ не использован. Попробуй ещё раз.» |
| 429 `rate_limited` | Кнопка неактивна до `Retry-After`, если он есть | `detail` или «Слишком много попыток. Подожди немного и попробуй снова.» |
| 5xx / сеть / таймаут | Неизвестный исход (§0.7) | См. §0.7 |
| Создание недоступно (режим `blocked` / `generation_off`) | Запрос не отправляется | Нейтральное сообщение (§0.4) |

Сообщения о том, что доступ «не потрачен», показываются только для ответов, где сервер это гарантирует (422 до транзакции, ARCH §11.2). Для неизвестного исхода таких обещаний нет.

### 0.9. Визуальная спецификация

**Идея.** SCR-03 показал анкету, SCR-04 принял код. SCR-05 — тихая пауза перед необратимым действием: те же подчёркнутые строки, тот же шрифт и ритм; никаких карточек, замков, щитов, предупреждающих плашек и праздничных эффектов. Единственный выразительный объект — чекбокс и кнопка. Сцена не двигается (К12).

**Токены — только существующие** (`ui/tokens.css`).

| Роль | Токен |
|---|---|
| Фон, сцена | `--cosmos-bg`, кадр `access` (= `review`) |
| Ответ в сводке, текст согласия | `--cosmos-text` |
| Подпись блока, вводный абзац, вторая строка | `--cosmos-muted` / `--cosmos-faint` |
| Подчёркивание | `--cosmos-line`; отмеченный чекбокс и акцент — `--cosmos-gold` |
| «Изменить», ссылки на документы, сообщение о расходе | `--cosmos-gold-light` |
| Ошибка | `--cosmos-danger` + иконка, как `Field` |
| Фокус | `--cosmos-focus` |

**Типографика** — как SCR-03/04: заголовок `clamp(40px, 3.6vw, 60px)` desktop / `clamp(32px, 8.6vw, 36px)` mobile, строка 2 — золотая italic serif; абзац 17/16px muted; подпись блока — микроподпись `Field`; ответ — 28px desktop / 24px mobile; вторая строка и ошибки — 15px; чекбокс — 24px, область нажатия не меньше 44×44; текст у чекбокса — 16–17px.

**Тексты** (Предложение, утверждает владелец; обращение на «ты»):

- Заголовок: «Последний шаг» / «перед твоим разбором.» (строка 2 — золотая italic serif). Не обещает, что разбор готов.
- Абзац: «Ещё раз взгляни на данные и доступ. После подтверждения начнётся создание разбора.»
- Блок АНКЕТА: ответ — имя; вторая строка — «12 марта 1990 · Казань · 14:30» (при неизвестном времени — «время неизвестно»; форматирование теми же функциями, что на SCR-03); действие «Изменить» → `/create/review` (доступное имя «Изменить данные анкеты»). Изменение анкеты инвалидирует отпечаток и ключ (§0.7).
- Блок ДОСТУП: ответ — «Код ••••7K2Q»; для скринридера — «код, оканчивающийся на 7 K 2 Q»; действия нет (другой код вводится на SCR-04 через «Назад»).
- Сообщение о расходе (К7, дословно): «При создании заказа будет использован один доступ.» Стоит непосредственно над чекбоксом, всегда видимо в режимах `ready`, `test`, `live`; не скрывается и не смягчается.
- Чекбокс: нативный `<input type="checkbox">` с кастомной отрисовкой; подпись — `<label>`. **Текст подписи — слот, заполняемый только утверждённой формулировкой (Q12).** До этого: в `blocked`/`generation_off` чекбокса нет; в `test` — заглушка из §0.5 п. 3. Ссылки «Условия использования» и «Политика конфиденциальности» стоят отдельной строкой под подписью (а не внутри `<label>`, чтобы клик по ссылке не переключал чекбокс), открываются в новой вкладке, анкета и сессия при этом не теряются. Пока SCR-14 не готов, ссылки не выводятся (К5).
- Кнопка: `PrimaryCTA` «Создать мой разбор» (SCREEN_SPEC §7; DESIGN_SYSTEM §7 называет «Создать разбор» — C-C6). Ссылка «← Назад» (на `/create/access`).
- Причина неактивной кнопки (для `aria-describedby`): «Отметь согласие, чтобы создать разбор.»
- Статусы: «Проверяем доступ…», «Создаём заказ…», «Проверяем, создан ли заказ…».
- Сообщения недоступности: `blocked` — «Создание разбора пока недоступно.»; `generation_off` — «Создание разборов сейчас недоступно. Анкета останется в этой вкладке — вернись позже.» (К11). Юридический статус и Q12 в тексте для пользователя не упоминаются.

**Прогресс.** `ProgressStep` остаётся полностью заполненным, как на SCR-03/04; счётчика нет.

**Что намеренно не используется:** карточки и рамки вокруг блоков, таблица «поле — значение», иконка замка/щита/предупреждения у согласия, красные плашки на расходе, фоновый «красный» оттенок сцены, конфетти, «вспышка» и движение камеры при отправке, предотмеченный чекбокс, плавающая или прибитая к низу кнопка, модальное окно подтверждения («Вы уверены?») — подтверждением служит чекбокс, второго диалога нет, процентов и «готово» нет.

### 0.13. Зависимости

**От SCR-04 / сессии:** кодовая сессия и `entitlement.id` с `state = available` (`GET /session`); отпечаток проверки; черновик в `sessionStorage`. SCR-04 не меняется. Замена сессии на SCR-05 не предлагается: другой код — через «Назад».

**От SCR-06:** принимает `order_id` из 201/200. До готовности SCR-06 переход ведёт на заглушку `/orders/:id/creating`. SCR-06 сам читает состояние заказа (`GET /orders/{id}` пока вне контракта) и не опирается на то, что SCR-05 «знает» о ходе генерации. SCR-05 не показывает и не обещает статусы генерации.

**От юридических документов:** тексты согласия, политики конфиденциальности и условий — Q12 (152-ФЗ: хранение персональных данных, передача провайдеру ИИ, трансграничность); страницы SCR-14 (`/legal/privacy`, `/legal/terms`) — сейчас заглушки; ссылки на них выводятся только когда документы утверждены (К5). До этого `creation_mode ≠ live`.

**От конфигурации:** `PublicConfig.consent_version`, `PublicConfig.legal_ready`, `features.generation` (все в контракте `0.3.0-6`). Пустая `consent_version` или `legal_ready=false` — режим `blocked`.

**От SCR-13:** «напиши в поддержку» в сообщениях — текст без ссылки, пока SCR-13 не готов (по прецеденту SCR-04).

### 0.14. Критерии приёмки

**Функциональные**

- Guard: неполная анкета → первый шаг; нет или устарел отпечаток → `/create/review`; аноним или истёкшая сессия → `/create/access` без потери анкеты; `consumed` → `/orders/:id`.
- Все состояния §0.4 воспроизводятся моками и тестовыми переключателями; тексты по §0.9; сообщение К7 присутствует дословно в режимах `ready`/`test`/`live`.
- Чекбокс не отмечен при каждом входе и после `consent_outdated`; без отметки запрос не уходит (клик и Enter).
- Режим `blocked` (по умолчанию): ни одного `POST /orders` во всех сценариях E2E без тестового режима.
- Режим `test` существует только на стенде с моками; в production-бандле нет кода тестового режима; баннер виден во всех кадрах тестового режима.
- E2E-06: валидный код → финальное согласие → один заказ, один расход доступа (на моке в тестовом режиме).
- Двойное нажатие, Enter, двойной тап — один `POST /orders`; две вкладки — один заказ (второй ответ 200 либо 409 `entitlement_used` с «Открыть разбор»).
- Неизвестный исход: сначала `GET /session`, новый ключ не создаётся, «Проверить ещё раз» уходит с тем же ключом, автоповторов нет.
- 422: доступ остаётся `available`, анкета сохранена, переход на review работает; текст «доступ не использован» показан только там, где это гарантия сервера.
- «← Назад» ведёт на `/create/access`, анкета и сессия сохранены; недоступен только в `submitting`/`recovering`.
- `features.generation=false`: создание недоступно, сообщение К11.
- Успех очищает черновик, отпечаток и ключ; код и тело запроса отсутствуют в URL, `sessionStorage`, `localStorage`, консоли и аналитике.
- Контракт: мок и клиент типизированы сгенерированной схемой; `make check-gen` чистый; `contract_test.go` проходит (после этапа API).
- axe без нарушений во всех состояниях; клавиатурный проход; reduced motion; без WebGL.

**Визуальные** (`make visual`, `?scene=freeze`): 1440×900, 1920×1080, 768×1024, 390×844, 375×667 — `ready`, `ready_checked`, `submitting` (`?orders=slow`), `unknown`, `blocked`, `generation_off`, `consent_outdated`, `entitlement_used`, 422, 429, тестовый режим с баннером, reduced motion. Колонка не заходит на планету; нет горизонтальной прокрутки; кнопки и ошибки не обрезаны; ошибок консоли нет; кадр сцены совпадает с SCR-04 (разница 0 пикселей). Утверждение владельцем по снимкам.

**Смена состояний**

- Отметка чекбокса: рамка → `--cosmos-gold`, заливка и галочка (`clip-path`/штрих) 160 мс; кнопка opacity 0.5 → 1 за 160 мс. Сообщение о расходе при этом не меняется.
- `submitting`: после 300 мс бегущая линия (`transform`), как SCR-03/04; управление глушится opacity 160 мс. Сцена не реагирует: ни вспышки, ни «ускорения» (M06: никаких обещаний готовности).
- Ошибка и неизвестный исход: строка под кнопками меняется кроссфейдом 160 мс (появление: opacity, сдвиг −4→0). Без тряски (MOT-03).
- Смена режимов блока подтверждения: кроссфейд 160 мс на месте.

**Выход.** Успех (подтверждённый `order_id`): колонка уходит влево 200 мс → `/orders/:id/creating`; само построение — M07 и зона SCR-06. «← Назад» — вправо, 200 мс; SCR-04 приходит слева.

**Reduced motion.** Колонка — opacity 200 мс, уход 120 мс; без сдвигов и blur; бегущая линия → статичный текст «Создаём заказ…»; галочка чекбокса появляется без прорисовки; перелёта камеры нет (MOTION §5).

**Без WebGL.** Постер; экран работает полностью.

- **Состояния:** `checking` («Проверяем доступ…» после 300 мс), `ready` / `ready_checked` (производное от чекбокса), `submitting` («Создаём заказ…» после 300 мс; чекбокс, «Изменить», «Назад» — `aria-disabled` и игнорируют действие), `recovering`, `unknown` («Проверить ещё раз» с тем же ключом), `blocked`, `generation_off`, `config_error`, `consent_outdated`, `entitlement_used` («Открыть разбор»), `error` (определённые отказы), `test` (баннер). Сводка берётся из черновика синхронно (снимок при открытии экрана, поэтому очистка черновика при успехе не пустит выход); маска — после чтения сессии в зарезервированной строке.
- **Идемпотентность:** `sessionStorage` `cosmos.order.attempt.v1` `{key, entitlementId, fingerprint, consentVersion, createdAt}` (TTL 24 ч). Ключ сохраняется при входе с теми же доступом, отпечатком и версией согласия; создаётся заново при смене любого из трёх, при `consent_outdated` и `idempotency_key_reused`; при неизвестном исходе и определённых отказах без изменения данных не меняется. Успех очищает ключ, черновик и отпечаток проверки. Защита от двойной отправки: `action` переключается синхронно до первого `await`, `inactive` вычисляется из него.
- **Неизвестный исход:** сеть, любой 5xx, успех без читаемого `id` → `recovering` → один `GET /session`; `consumed` и тот же `entitlement.id` → переход к SCR-06; иначе `unknown`. Автоповторов нет.
- **Ошибки:** 401 → access; 403 `creation_unavailable` → режим `blocked` (создание закрывается); 404 `not_found` → повторное чтение сессии и конфигурации (в контракте — чужой `entitlement_id`; в §0.8 такой строки нет, см. отклонение 2); 409 `consent_outdated` → сброс чекбокса, перечитать `GET /config`, новый ключ, фокус на чекбокс; 409 `entitlement_used` → `GET /session`, «Открыть разбор»; 409 `entitlement_blocked`; 409 `idempotency_key_reused`; 422 профиль → «Проверить и изменить»; 422 `calculation_failed`; 429 (`Retry-After`). Анкета и кодовая сессия не очищаются ни одним отказом.
- **Движение (M06) и reduced motion:** вход колонки одним слоем (opacity, сдвиг 20→0, blur 2→0, 420 мс, `out`; reload — подъём), кроссфейд 160 мс слота подтверждения и строки статуса, чекбокс — рамка, заливка и прорисовка галочки `clip-path` 160 мс, кнопка 0.5 → 1, бегущая линия при `submitting`/`recovering`, выход колонки влево (успех, «Открыть разбор») и вправо («Назад», «Изменить»). Reduced motion: только opacity 200 мс, галочка без прорисовки, бегущая линия скрыта (остаётся текст статуса). Сцена не реагирует ни на что.
- **Отклонения и допущения (на утверждение владельца):**
  1. Режим `live` не реализован (Р-C10): в коде нет пути, по которому открытая настоящая конфигурация разрешила бы отправку.
  2. Ответ 404 `not_found` обработан как устаревший доступ (перечитывание сессии): таблица §0.8 такой строки не имела.
  3. «Причина неактивной кнопки» («Отметь согласие, чтобы создать разбор.») скрыта визуально и связана через `aria-describedby`; на экране отдельной строки нет (каркас §0.10 её не содержит).
  4. В `config_error` основная кнопка меняет подпись на «Проверить ещё раз» и повторяет чтение (как `unknown`); текст ошибки — в слоте подтверждения, а не под кнопками, чтобы слот сохранял высоту.
  5. Ссылки на документы не выводятся (К5, C-C7); место под подпись согласия — слот, заполняемый только в dev-сборке заглушкой.
  6. Баннер тестового режима вставлен между `ProgressStep` и заголовком; в тестовом режиме он сдвигает заголовок на высоту своей строки (на production баннера нет).
