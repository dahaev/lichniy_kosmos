# Личный космос 2.0 — MOTION_SPEC v1

**Статус:** motion-проект для MVP; конкретные времена — стартовые рекомендации на тестирование, а не данные, восстановленные из скриншота.

## 1. Принципы
1. **Motion narrates meaning**: анимация помогает понять переход от человека к карте и результату, а не отвлекает от действия.
2. **One continuous cosmos**: сцена фона может перетекать между экранами; текст остается ясным и интерактивным.
3. **No fake computation**: UI отражает реальные server state, не рисует выдуманный процент готовности.
4. **Non-blocking**: skip/refresh/открытие другой вкладки не останавливает генерацию и не создаёт второй заказ.
5. **Performance & accessibility first**: reduced motion, fallback, управление памятью GPU, mobile tiers.

## 2. Библиотечные роли
- Vue Router управляет маршрутами и доступностью экранов.
- Motion for Vue отвечает за переходы текста, формы, CTA, микровзаимодействия и exit/enter (при поддержке версии).
- Three.js отвечает **только** за фон/планеты/орбиты и реалистичную/художественную сцену.
- Pinia/доменные composables хранят UI state, API state, анкеты и статусы; WebGL не является источником истины.
- `requestAnimationFrame` и активность WebGL настраивать по видимости, не плодить несколько render loops.

## 3. Motion tokens (предложение)
| Класс | Длительность | Применение |
|---|---:|---|
| Micro | 120–220 мс | hover/focus/стрелки |
| Field/step | 320–550 мс | переход одного поля анкеты |
| Route | 500–900 мс | hero → анкета и обратно |
| Camera transition | 900–1800 мс | смена композиции 3D-сцены |
| Major reveal | 1800–3500 мс | визуальная последовательность карты |
| Ambient | непрерывно, очень медленно | звезды, орбиты, свет, без дерганий |

Easing: мягкий ease-out для контента; кинематографичная ease-in-out для камеры; **не использовать** bounce/elastic ради декоративности. Для long-running ambience не привязывать длительность к ответу backend.

## 4. Основной storyboard

### M01 — Первый визит `/`
- Уже видна планета, звезды и горизонт. Сначала появляется контрастный заголовок (не позже окончания первого видимого кадра загрузки), затем подзаголовок и CTA.
- Допустим очень медленный drift звезд и glow, параллакс только при поддержке и умеренной амплитуде.
- CTA работает даже если 3D ассет ещё загружается.

### M02 — Hero CTA → `/create` (не создаёт заказ)
1. Пользователь нажимает «Построить мою карту».
2. CTA дает мгновенный отклик; фон начинает непрерывное смещение камеры/позиции планеты.
3. Типографика hero мягко исчезает, появляется счётчик `01/04` и первый вопрос.
4. Устанавливается фокус на заголовок/первое поле с учётом клавиатуры и screen reader.
5. Если WebGL недоступен — затемнение/crossfade фоновых изображений, без потери данных.

### M03 — Анкета: 4 шага
- Один вопрос/семантическая группа на экране.
- Enter/Далее выполняет валидацию **до** выхода; при ошибке остается на шаге, подсветка и текст ошибки.
- Уходящий блок смещается на 10–24px и исчезает, следующий появляется из обратного направления (ориентир 400 мс).
- Сохранить значения в draft; Back анимируется обратным направлением; промах валидации не прыгает между экранами.
- При выборе «время неизвестно» плавно сворачиваются дополнительные поля, а не исчезают мгновенно.

### M04 — `/create/review`
- Четыре введённых параметра появляются последовательными мягкими акцентами (stagger), но доступны для чтения сразу.
- Любая кнопка «Изменить» возвращает к нужному шагу без потери draft.
- CTA не создаёт заказ; только ведёт к доступу.

### M05 — `/create/access` и OTP
- Активация воспринимается как доступ к персональному опыту, **но не утверждает, что карта уже создана**.
- Ошибки показываются рядом с полем без тряски всей сцены.
- OTP может открываться как отдельный маршрут, сохраняет гостевой draft; серверные ограничения не подменять анимацией.

### M06 — `/create/consent` → создание заказа
- После явного согласия и финального клика UI показывает `submitting`; **никаких обещаний готовности** до подтверждённого ответа API.
- Server-side idempotency key обязателен; двойной клик и retry не должны расходовать код дважды.
- Если создание не удалось до фиксации — вернуться к ошибке с сохранением данных. Если исход неизвестен — восстановить результат по API прежде чем предлагать повтор.
- После подтвержденного order ID перейти к сцене `/orders/:id/creating`.

### M07 — Главная cinematic-сцена построения (реальный заказ)
**Два независимых state machines:**
- `renderPhase`: `initial` → `celestial_arrival` → `orbital_alignment` → `chart_reveal` → `ambient` / `complete`.
- `serverPhase`: `queued` → `writing` → `illustrating` → `ready`, плюс `failed_retryable`, `needs_review`, и возможные промежуточные этапы по утвержденному API.

**Кадры:**
1. `initial` — камера перемещается в композицию из звезд, появляются мягкие ориентиры/кольца.
2. `celestial_arrival` — десять тел проявляются постепенно. Их подписи и знаки основаны на **серверных рассчитанных данных**; художественная траектория допустима, ложные положения — нет.
3. `orbital_alignment` — тела перемещаются к отображаемым позициям карты, мягко проявляются аспекты. Не обещать физически точную 3D-модель движения небесных тел.
4. `chart_reveal` — упорядоченная композиция трансформируется в читаемую натальную схему; показать информацию о неопределённости.
5. `ambient` — если backend работает дольше, сцена спокойно продолжается без фальшивого процента. Реальный статус: «Создаём текст», «Готовим иллюстрацию».
6. `complete` — только при `serverPhase=ready` доступен переход к полному результату; при частичном состоянии — показ доступных частей без обмана.

**Время:** первая хореография ориентировочно 8–15 секунд, но пользователь может пропустить её сразу. Время работы сервера независимое; отсутствие конца первой анимации не означает ошибку.

**Неизвестное время рождения:** планеты и уверенно известные данные показываются, **никаких вымышленных ASC/MC/домов**; UI объясняет ограничение.

**Ошибки и восстановление:**
- `needs_review`: остановка платного повтора, сообщение и путь поддержки; показывать уже принятые материалы.
- `failed_retryable`: только разрешённая сервером операция продолжения недостающего этапа.
- Refresh/возврат напрямую по URL: получить serverPhase + данные заказа; не запускать ещё один заказ или ИИ самостоятельно.

### M08 — Создание → результат `/orders/:id`
- При полной готовности 3D-сцена постепенно уступает место странице разбора: кольца становятся рамкой/линиями карты, затем раскрываются заголовок и текст.
- Кнопка «Перейти к разбору» доступна без ожидания декоративного окончания.
- Удерживать keyboard focus при переходе; не захватывать колесико прокрутки.
- Частичный текст и картинка оформлены честно, PDF — только когда есть нужные материалы.

### M09 — Кабинет/результат/возврат
- Переходы спокойнее и быстрее, чем hero/creation.
- Возвращение к готовому заказу **не** повторяет длительную сцену построения и не запускает генерацию.
- Пользователь может явно пересмотреть визуализацию при наличии данных, но это только playback без вычислительных вызовов.

## 5. UX controls
- Кнопка `Пропустить анимацию` у сцены создания видима и доступна с клавиатуры.
- `prefers-reduced-motion`: отключить camera fly-through, параллакс, орбитальный motion и stagger; перейти к короткому fade или статичным состояниям. Реальные статусы сохраняются.
- `visibilitychange`: снижение FPS/пауза canvas в скрытой вкладке без остановки server job.
- Ошибка WebGL/медленная загрузка ассета → статичный background fallback и текстовые статусы.
- Никаких autoplay-звуков. Звук, если когда-то появится, только по явному действию.

## 6. Производительность
- Desktop target: плавное взаимодействие с ориентиром 60 FPS на целевых машинах; mobile может выбирать 30 FPS или статичный режим на слабых устройствах.
- Ограничить DPR/текстуры и draw calls по адаптивному quality tier; не блокировать ввод при загрузке 3D.
- Dispose geometry/materials/textures, event listeners, RAF при unmount; слушать WebGL context lost/restored.
- Стараться избегать длинных задач на main thread; если расчёт происходит на Go-сервере, не повторять сложные вычисления в браузере.
- Метрики: FPS, WebGL failures, duration of transitions, LCP/CLS/INP для публичной страницы; цели фиксировать после базового профилирования.

## 7. Матрица тестов и критерии приёмки
| ID | Проверка | Ожидаемое |
|---|---|---|
| MOT-01 | Hero CTA | переход в анкету без авторизации и без API создания заказа |
| MOT-02 | Back/Forward анкеты | значения и прогресс сохраняются, анимация по направлению |
| MOT-03 | Ошибка поля | не теряется ввод, нет мерцаний и прыжков фокуса |
| MOT-04 | Финальная кнопка | анимация вычисления только после принятого заказа |
| MOT-05 | Двойной клик / retry | только один заказ и один расход доступа |
| MOT-06 | Медленный AI | ambient loop, реальные статусы, нет фальшивого % |
| MOT-07 | Refresh во время генерации | реальное состояние заказа без повторного ИИ |
| MOT-08 | Unknown birth time | отсутствуют неподтверждённые дома и углы |
| MOT-09 | Ready | корректный переход к результату и сохранённым файлам |
| MOT-10 | Reduced motion | все функции доступны без 3D-перелёта |
| MOT-11 | Weak device / WebGL lost | fallback не блокирует использование |
| MOT-12 | Direct URL to result | страница доступна по разрешённой сессии, без повторной кинематографичной сцены |

## 8. Неопределённости до реализации
1. Нет видео/кода анимации утверждённого hero: timing нужно подбирать и утверждать на работающей версии.
2. Нужны утверждённые ассеты планеты, звездного поля и горизонта, лицензии и уровни детализации.
3. Реальная модель `Chart`/API-формат определит маппинг рассчитанных значений на орбитальную композицию.
4. Решить, как пользователь видит статус расчёта, если сервер быстро создает карту еще до появления сцены; не имитировать продолжающийся backend-расчёт.
